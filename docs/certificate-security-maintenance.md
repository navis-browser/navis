# Offline certificate security and maintenance

Navis validates TLS locally using NSS, the reviewed application trust store, a compiled OneCRL baseline and Certificate Transparency (CT). Linux, Windows and Android require CT mode 2 for publicly trusted roots. Persisted mode 0 and CT exemption lists cannot override product policy. The upstream treatment of private/user-managed roots remains intact.

`runtime/vendor/gecko.json` selects an exact official released Gecko ESR baseline. Its complete upstream update review covers commit history, final source differences, security advisories and every retained semantic adapter, following the [Runtime update contract](https://github.com/navis-browser/runtime/blob/main/docs/gecko-esr-update-review.md). Updates take the reviewed release tree as a whole. A certificate incident does not select which unrelated upstream security fixes Navis receives.

`runtime/config/certificate-security-data.json` binds certificate data to that Gecko pin and its paired NSS implementation version. It records official source revisions/URLs, SHA-256 hashes, the full OneCRL snapshot identity, the complete root-list snapshot and matching version header, and the actual CT expiry. `navis/config/certificate-security-policy.json` sets the release thresholds. Builds consume frozen files; they never download a moving log list. `runtime/scripts/generate-certificate-security.py` renders the native revocation table and shared diagnostic metadata deterministically. The hash-owned Gecko port contains the corresponding source data and generated header.

The native TLS trust path checks both OneCRL issuer/serial and subject/SPKI-hash entries before reading mutable certificate storage. This baseline is already available at the first handshake, offline, without a Profile import or asynchronous startup task. It also covers revoked cross-signs with the same subject/public key. The normal OneCRL storage consumer additionally receives the applicable upstream bundle-at-initialization fix. A changed profile database cannot remove the application baseline.

The NSS implementation follows the selected Gecko release. When newer trust data is required, review and take the complete root list and matching `nssckbi.h` from an exact official NSS release. Upstream's version-header guidance allows older branches to take the most recent list. Check data-format compatibility with the paired NSS implementation; include every upstream addition, removal and trust-attribute change. The packaged list must equal the reviewed upstream snapshot byte for byte. The manifest rejects a selective root-removal scope or a mismatched list/header version. User-managed trust remains governed by the retained NSS behavior.

OneCRL takes the complete official record response, preserving all record fields under the manifest's deterministic normalization. CT takes a complete reviewed official log-list snapshot and its real expiry. A required upstream fix outside the selected release must have its own exact revision, applicability review and bounded semantic port; remove the extra adaptation once a later baseline supplies it. Incident certificates may remain regression fixtures. Production verification uses the general trust, revocation and CT rules.

## Release procedure

1. At each maintenance release, check Mozilla's official ESR release metadata, release/build tags and all security advisories since the accepted pin. Prepare a candidate pin and run `runtime/scripts/review-gecko-esr-update.py` with complete relevant history. Review every commit queue, final changed-path inventory and semantic-port intersection, including calls into changed upstream interfaces. Record the review conclusion before adopting the pin. A path inventory, successful patch application or advisory subject match alone does not establish compatibility or reproduce an individual vulnerability fix.
2. Review complete official CT, OneCRL and root-list snapshots and applicable initialization fixes. Record exact revisions or response hashes, normalization, packaged hashes, the root-library/header version and actual CT expiry in the shared manifest. Keep the NSS implementation paired with Gecko. Reconstruct the full ordered semantic-port series independently, then run the offline generator in check mode, certificate-security tests, exact settings policy checks and independent CT/revocation fixtures. Source packages include the generator, manifest and all ports. Never advance an expiry without replacing the upstream metadata that supplies it.
3. Run `python3 navis/scripts/verify-certificate-security.py` before source freeze/build. It rejects a different Gecko/NSS baseline, partial root snapshot or mismatched version header. The actual CT metadata must have at least **42 days** remaining, with effective product mode 2 and no Remote Settings update dependency. Invalid/missing data, a hash mismatch or less remaining time blocks the candidate.
4. Freeze the complete project source and use one new BuildID for Linux, Windows and Android. Run the same gate on each extracted desktop archive (`--runtime PATH`) and Android APK (`--apk PATH`). It verifies packaged prefs/data and the native verifier's snapshot identity, so a new omni beside an old native engine is rejected.
5. A Gecko pin change requires clean preparation, clean builds and the full applicable Runtime, navigation, Fission, sandbox, crash, capability and package regression matrix. Test the new desktop packages with normal HTTPS, revoked original and cross-sign certificate fixtures, independent sufficient/missing/invalid SCT cases, fresh and stale Profiles and offline first startup. Capture exact certificate error codes; an unrelated revocation, expiry or network error does not prove CT rejection. Test CT expiry boundaries with controlled verification times rather than changing a host clock. Preserve private-root behavior. Android package evidence and physical-device acceptance remain separate.
6. **Rerun all three package gates at actual handoff**, even if the original build passed. Store the gate time, remaining validity, source/BuildID and package hashes with the release receipt. A gate result from weeks earlier cannot authorize distribution today. Check the localized security-data status/expiry in Support information.

While a Navis release is maintained, a maintainer must prepare a same-source three-platform security maintenance release at intervals of **no more than 28 days**, including periods with no feature release. Each handoff receipt records the accepted upstream revision, review dossier and conclusion hashes, security-data manifest hash, source freeze, three package identities, gate times, CT expiry and next maintenance deadline. The next deadline is the last handoff time plus 28 days; check it when preparing the next release. A critical upstream fix, CA compromise or CT-log disqualification requires an urgent reviewed update outside that interval, followed by the same complete baseline/data review. This is a maintainer obligation, not a background browser service or an unattended agent task.

## Expiry and offline operation

Support information shows the bundled revocation date, CT expiry in UTC and an explicit current/expiring/expired state. The expiring state begins when fewer than 28 days remain. Under the retained upstream safeguard, verification after the CT list's expiry skips CT enforcement; mode 2 alone does not prevent that. The expired state explicitly says enforcement has stopped and asks the user to install a current package. Navis does not silently block every public HTTPS site on expiry or extend old metadata timestamps.

Application packages are the update channel for trust, OneCRL and CT metadata. The user chooses when to install them. There is no background Mozilla Remote Settings poll, attachment download, signature-chain fetch, new Navis updater or unsigned data-import path. Website TLS, CA OCSP and user-requested browsing remain normal network operations; they are distinct from a browser-product settings service. An installation that is never updated cannot retain current CT or emergency revocation knowledge indefinitely.

Certificate error documents retain the native verifier's exact error and recovery restrictions. Navis explicitly disables Firefox's MITM priming preference on every platform; error-page initialization must not depend on a missing Firefox default or request its browser-specific probing service. Desktop defaults also supply `security.certerrors.permanentOverride=true` for the upstream acceptance action. This does not trust invalid certificates automatically: only explicit user acceptance records an exception for the failed host, port and certificate. Normal-window exceptions persist, a user preference of `false` makes them temporary, and private-window exceptions are always temporary. HSTS and other non-overridable failures retain their native restrictions.

Run `node --test navis/tests/certificate-error-actions.mjs` against the prepared pinned Gecko source to check the actual upstream action with product defaults, temporary/private acceptance and native rejection. The source and extracted-package certificate gates both require the desktop default. Packaged desktop regression must also navigate to an isolated self-signed HTTPS server with WebDriver's `acceptInsecureCerts=false`, confirm the exact certificate error, activate the real acceptance button and verify the server content is reached. Check persistence after restart, rejection on a different port or changed certificate, and private-window exception cleanup; presenting an error page alone does not verify recovery.

## Withdrawing accepted certificate risks

Desktop site information identifies a connection that actually used a certificate exception and offers **Revoke exception and reload**. Runtime authenticates the owned current HTTPS Session and revalidates its navigation, fingerprint and private/normal sharing before invoking Gecko's native removal and cache-bypassing reload. A private page using a normal-browsing fallback explicitly explains that revocation also removes the matching normal exception. Matching private and fallback records are removed together; other sites, ports and certificates remain intact.

Settings / Privacy and security lists the native normal-browsing exception inventory with host/port and SHA-256 fingerprint, and provides individual revocation. Private entries never enter this list. The native enumeration lacks permanence metadata, so the UI does not label every entry as saved. Opaque offered IDs are revalidated against the live native record; stale or forged targets fail without deletion. Settings removal invalidates native TLS sessions and connections; existing documents need a reload to recheck their certificate. No custom trust database, manual Profile-file editing, remote service or root-store modification participates.

The packaged-product regression accepts a controlled self-signed HTTPS fixture with `acceptInsecureCerts=false`, invokes both real UI withdrawal paths, and verifies the original certificate warning returns. It retains an unrelated site's exception, checks native private fallback and temporary cleanup, and distinguishes those native outcomes from deterministic stale/foreign/forged-request tests. Tests use disposable Profiles rather than the user's existing exceptions.
